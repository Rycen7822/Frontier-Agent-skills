# Whole-repository audit and collaboration

Use when the user explicitly requests comprehensive manual coverage, or authorized parallel work needs coordinated boundaries. A selected component audit remains scoped to that component and relevant consumers.

## Define the actual scope

Bind conclusions to current source state and the selected working-tree or revision scope. Account for applicable user work. Inventory maintained implementation, tests, build and operational entrypoints, with generated and adopted artifacts identified separately. File extensions alone can miss launchers, alternative module suffixes or build declarations; reconcile the inventory against real loading and delivery paths.

State meaningful exclusions and external dependencies. Read relevant architecture decisions, configuration, build and host contracts as context. For generated bundles, check maintained source, generation and actual loading; do not count duplicate generated lines as independent manual understanding. Binary presence or a hash does not establish source behavior.

## Read and record real progress

Manually read the implementation in bounded contiguous sections, including assigned tests and callers needed to understand a rule. Searches, graphs, metrics and reading only headers or tails do not satisfy a request to read whole files.

Keep concise temporary notes as meaningful observations or decisions emerge, before long work or a handoff can lose them. Reuse existing state rather than creating mirrored logs. For a full audit, track assigned files, actual read ranges, a brief responsibility judgment and outstanding gaps. A partially read file stays partial. Keep a note of useful no-change decisions and counterevidence, not only defects.

Coverage tooling can reconcile ranges and source freshness; it cannot certify understanding. If source changes, refresh affected conclusions and coverage rather than blindly replaying all reads. Do not force a new ledger format, timing quota or scripts when the existing record suffices.

## Coordinate only authorized parallel work

Choose independent work units when their benefit covers coordination cost. The user's concurrency allowance is an upper bound, not a target. No fixed model, role count or nested delegation is required. One primary owner keeps shared classification, task scope, integration and final conclusions.

Give each worker the objective, source scope, current constraints, architectural questions, allowed writes and completion condition. Workers read implementation and consumers themselves, maintain owned temporary notes and deliver findings with source, conflict, affected consumer, counterevidence and a minimal direction. Findings count is not a completion condition.

For analysis, keep product code read-only and worker artifacts separate. For authorized implementation, isolate overlapping edits and preserve one integrating owner for shared contracts. Investigating adjacent consumers does not grant edit authority outside the task.

As a worker becomes available, transfer worthwhile unread items with their state and context. Update the original assignment, new assignment and primary scope; an item transferred unread must not count as completed in both groups. Scheduling slices are not proposed architecture categories.

## Perform primary review

Check delivered artifacts and decisive evidence, not just completion messages. Revisit high-impact ownership claims and cross-group consumers. Resolve contradictions, distinguish stale snapshots from current failures, combine one root cause's manifestations and record why a plausible concern was cleared or narrowed.

Use targeted cross-review for a consequential unresolved issue, not a mandatory second reviewer for every file. Separate reproduced defects, source-confirmed paths, structural debt, taste observations and unknowns. Do not manufacture tests or independent model calls to decorate a source-based conclusion.

## Close the requested work

Reconcile unread files, missing consumer context, changed source and unavailable evidence before claiming full coverage. Report those limits explicitly. Full reading is neither a guarantee of defect absence nor a reason to keep searching indefinitely after the requested scope is complete.

When improvements are authorized, implement coherent responsibility slices and check their consumers. Follow Test Behavior for authored checks and obligations that end. Recheck that the resulting abstraction belongs in the right layer and has not transferred policy, ordering or cleanup into callers.

Report proposals or implemented outcomes, retained responsibilities, withdrawn claims and remaining uncertainties. Classify source, tests and generated changes separately if reporting volume. Account for workers and temporary resources started for this task while preserving user sessions and useful evidence.
